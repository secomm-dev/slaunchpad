# [SLP][TASK-H9ZT7G] Repair Dangling Region References Blocking MSI Source Form After 2025 Scheme Sync

Generated by Secomm Production AI Toolkit

## Summary

Admin Stores → Inventory → Sources: the State/Province (region_id) field never renders.
Root cause is NOT the cascade JS (TASK-9JZNJ2 fixed that) but **dangling data**: the 2025
VN scheme sync rebuilt `directory_country_region` with new ids (34 provincial units, ids
from 1191; HCM = 1205/VN-15) while `inventory_source.default` still stored `region_id=1185`
(old-scheme HCMC). The vendor element
`Magento_InventoryAdminUi/js/form/element/region` calls
`this.indexedOptions[value].label` unguarded in `setDifferedFromDefault` —
`indexedOptions[1185]` is undefined → TypeError during value hydration → component init
fails → the whole field never renders.

DB audit (same defect class, active references only repaired here):
`inventory_source` 1, `customer_address_entity` 2, `quote_address` 35,
`sales_order_address` 13 (51 total). Config: `shipping/origin/region_id=1185` (dangling,
affects shipping origin) while `general/store_information/region_id` was already updated to
1205 — i.e. the scheme import updated store information but did NOT remap other core
directory references.

## Mini Spec

### Goal

Restore the MSI source form State/Province field by repairing the two ACTIVE dangling
references (source record + shipping origin config) to the new-scheme id, without touching
historical or PII data.

### Expected Behavior

- `inventory_source.default`: `region_id=1205`, `region='Ho Chi Minh'` (preserves the
  existing HCMC intent; saved city 'Phu My Ward' untouched — cascade prefill drops or keeps
  it per the documented first-level-match rule).
- `core_config_data` `shipping/origin/region_id` = 1205.
- State/Province renders on the source form with the 34 new-scheme provinces, HCM selected.
- Historical data (quote_address, sales_order_address) and PII (customer_address_entity)
  are NOT modified — owned by TASK-2FQJHX.

### Constraints / Rules

- DB change = Tier-2 area: repair executed on LOCAL DEV DB only, guarded + idempotent
  (`WHERE ... AND <old value>`), plan-approved by user this session; TL review required.
- Vendor code is not modified (the unguarded vendor lookup stays as-is; data must stay
  referentially valid).
- Repair value choice: 1205 (new-scheme HCM) instead of NULL to keep the origin address
  semantically intact.

### Out of Scope

- Systemic remap of the 51 dangling refs + importer step (TASK-2FQJHX, tbd — Tier 2).
- Hardening the vendor `region.js` lookup (no vendor patches).

### Acceptance Criteria

- AC-1: Source form renders State/Province with 34 new-scheme provinces; HCM preselected.
- AC-2: `shipping/origin/region_id` resolves to an existing region (1205).
- AC-3: Region change → city cascade level loads; save + reload keeps prefill.
- AC-4: Validator FAIL count unchanged vs baseline 56.

## Approach

Two guarded UPDATEs on the local dev DB (`launchpad` @127.0.0.1:3307), then
`bin/magento cache:clean config`. No code change.

## Implementation Notes

- Diagnosis chain: vendor `region.js` (`setDifferedFromDefault` →
  `indexedOptions[value].label`, unguarded) + dangling 1185 confirmed by
  `SELECT ... WHERE region_id=1185` returning empty; new-scheme HCM = 1205 (VN-15) read
  from `directory_country_region`.
- The same dangling value also existed in `shipping/origin/region_id` — repaired in the
  same pass because it is an active shipping-calculation input, not history.
