# [SLP][TASK-1WKX9C] Keep Hidden Methods Visible To Carrier-Limited Save Validation Collects

Generated by Secomm Production AI Toolkit

## Summary

Fix the HTTP 404 `Carrier with such method not found: mptablerate, 8` on checkout
`shipping-information` for OUTER-district addresses. The customer-facing estimate for those
addresses runs GHN (in scope there per `destination_scope=ALL_EXCEPT_SELECTED_ZONES`); when
GHN fails with a fallback-eligible outcome, `FallbackCoordinator` appends a copy of the
HIDDEN fallback method (`mptablerate` Standard, `show_to_customer=0`) — the customer selects
it. Magento's save flows then re-collect with `limitCarrier` set (only mptablerate runs, the
ShippingCore outcome collector stays EMPTY, so the fallback cannot re-append) and the
visibility filter strips the hidden method — core's rate check then rejects exactly the rate
the system itself offered. Fix: treat hidden-method stripping as the customer-facing
presentation rule it is — apply it only on non-limited collects.

## Mini Spec

### Goal

`CollectRatesPlugin` (the outer rate-collection seam) must NOT strip `show_to_customer=0`
methods from a carrier-limited collect (`RateRequest::getLimitCarrier()` non-empty), while
keeping the strip for customer-facing (non-limited) collects unchanged.

### Expected Behavior

- Outer address: estimate still offers `mptablerate_8` (fallback copy) AND
  `shipping-information` / `payment-information` with `mptablerate_8` succeeds (200).
- Inner address: estimate still hides `mptablerate_8` (filter runs — no change).
- Known trade-off (accepted, documented): a save posting an un-offered hidden method code
  now validates if that method's own rates match the address (save-validation collects keep
  hidden methods). Hidden methods remain unselectable through the UI everywhere; Magento's
  model is "any collected method code may be posted" — `show_to_customer` stays a
  presentation flag, not an entitlement.

### Constraints / Rules

- NO core/vendor edits; the 3 core `setLimitCarrier` callers
  (`ShippingInformationManagement`, `PaymentInformationManagement`,
  `GuestPaymentInformationManagement`) are untouched — fixing at the seam covers all.
- `MethodVisibilityFilter` itself is unchanged; the guard lives in `CollectRatesPlugin`.
- FROZEN: ShippingCore runtime (no change — the empty-collector early return in
  `FallbackCoordinator` is untouched; the fix makes it irrelevant for limited collects).
- Fallback presentation, fallback eligibility policy, zone scoping: unchanged.

### Out of Scope

- Making `FallbackCoordinator` append fallback copies during limited collects (impossible
  cleanly: no primary-carrier outcome exists under the limit).
- Backend strictness for hand-crafted method-code POSTs (Magento-native behavior).
- The stale-localStorage client defect — that is TASK-9ZEM73 (separate mechanism, fixed
  independently; its heal mixin stays).

### Acceptance Criteria

- AC-001: REST reproduction (guest cart, Gia Lam outer district): estimate returns
  `mptablerate_7` + `mptablerate_8`; save `shipping-information` with `mptablerate_8`
  returns 200 (pre-fix: 404 with `["mptablerate","8"]`).
- AC-002: Estimate for Bach Mai (inner district) still returns ONLY `mptablerate_7` — the
  visibility filter still strips hidden methods on customer-facing collects.
- AC-003: Unit regression: limited collect → `MethodVisibilityFilter::filter()` never runs;
  non-limited collect → runs exactly once (`RateCollectionMatrixTest`, +2 tests).
- AC-004: Full `Launchpad_MageplazaTableRate` unit suite green.
- AC-005: Record + evidence complete; validator clean for this record.

## Approach

Single seam, single condition in
`Launchpad\MageplazaTableRate\Plugin\Shipping\CollectRatesPlugin::aroundCollectRates`:
wrap the existing `$this->visibilityFilter->filter($result)` in
`if (!$request->getLimitCarrier())`. `appendFallbackRates` stays unconditional (its own
empty-collector guard already no-ops it on limited collects).
