# [SLP][TASK-9ZEM73] Heal Stale OSC Shipping Selection and Clear Sticky Checkout Error Notices

Generated by Secomm Production AI Toolkit

## Summary

Fix the OSC checkout UX defect where the notice `Carrier with such method not found:
mptablerate, 8` appears on page load (with a pre-filled address) and after selecting a city,
and then NEVER disappears even though rates load correctly. Two client-side root causes:
(1) a stale persisted shipping selection in the browser localStorage (`checkout-data
.selectedShippingRate = 'mptablerate_8'` — a method now hidden from every rate list by the
Launchpad visibility filter) is never cleared when it stops matching; (2) the global
`Magento_Ui` message list is never cleared when a later save succeeds, so the error notice is
sticky forever. Fix = two JS mixins in Launchpad_Osc (owner of all OSC coupling per
DEC-TASKFMAN1B). Server throw is CORRECT core behavior and is not changed; hiding the
fallback-only method is intended design (TASK-5XQXZK / FEAT-FQWEQ3 coverage work).

## Mini Spec

### Goal

1. **Self-healing selection**: after every rate resolution, if no rate matched the stored
   `selectedShippingRate` (quote.shippingMethod() ended up null) → clear the stored selection
   so the stale code can never be re-applied on later page loads / rate reloads.
2. **Non-sticky notices**: when a shipping-information save SUCCEEDS, clear the global
   message list (the same container the failure path wrote to) so stale error notices
   disappear as soon as the checkout state is valid again. New failures still render.

### Expected Behavior

- Browser with a stale stored selection: first page load after deploy heals localStorage;
  no POST carrying the dead method code; no error notice.
- User selects city / changes address → rates reload; if the previously chosen method is no
  longer offered, selection resets silently (no error notice, no failed save).
- Any real server error still renders via the normal errorProcessor path; it clears on the
  next successful save.
- Valid selections and the native auto-select-single-rate behavior are untouched.

### Constraints / Rules

- NO core/vendor edits, NO `app/code/Mageplaza/*` edits (preference-subclass/mixin only via
  Launchpad_Osc — same boundary as DEC-TASKFMAN1B).
- Do NOT swallow server errors and do NOT change `ShippingInformationManagement` semantics
  (the NoSuchEntityException for a method outside the collected rates is correct).
- Do NOT change rate collection / MethodVisibilityFilter / fallback design (TASK-5XQXZK,
  FEAT-FQWEQ3 frozen outcomes).
- Mixins must compose with the EXISTING mixins on the same targets
  (`Secomm_AddressDropdown`, `Mageplaza_DeliveryTime`, `Mageplaza_OscPro`) — additive
  wrapSuper only, no re-implementation of the POST.
- Clear only on SUCCESS of the same save flow that can produce the error — never clear
  proactively in a way that could hide a just-reported error.

### Out of Scope

- Server-side swallowing of the NoSuchEntityException (rejected: hides real config errors).
- `Secomm_AddressDropdown` save-processor `cache[0]` fallback (sends first cached rate when
  no method selected) — potential follow-up, NOT this ticket.
- OSC "loading speed" optimization modes (OscPro refresh_page variants) — behavior must be
  correct in the current store config; no tuning of those modes.
- Admin-side validation gap (core mapRules) — separate known follow-up.

### Acceptance Criteria

- AC-001: With localStorage `checkout-data.selectedShippingRate` set to a code absent from
  the rate list (e.g. `mptablerate_8`), first checkout load heals the stored value (resets to
  null) and NO `shipping-information` POST carries the dead method code.
- AC-002: A previously rendered error notice in the global message list is cleared when the
  next shipping-information save succeeds (rates render, notice gone).
- AC-003: With a valid selection (method present in the list), behavior is unchanged:
  selection is preserved across rate reloads; native single-rate auto-select still works.
- AC-004: Existing mixin chains still function (Secomm_AddressDropdown save payload,
  DeliveryTime delivery fields, Osc loader) — checkout save flow works end-to-end.
- AC-005: Evidence recorded in `.ai/runtime/evidence/TASK-9ZEM73/` (browser flow notes);
  `bin/project-ai-validate --check-specs --check-identity` green for this record.

## Implementation Notes

(2026-09-25) Implemented per Approach. Files:
- `app/code/Launchpad/Osc/view/frontend/web/js/action/select-shipping-method-mixin.js` (new)
  — heals the stored `selectedShippingRate` whenever `select-shipping-method(null)` fires
  while none of the currently loaded rates offers the stored code. Chosen over wrapping
  `checkout-data-resolver.resolveShippingRates` because `select-shipping-method` is the
  single writer funnel for quote.shippingMethod (verified: no other module mixins it), so the
  heal is independent of resolver mixin order (OscPro's wrapSuper re-implementation would
  bypass a resolver wrapper applied before it).
- `app/code/Launchpad/Osc/view/frontend/web/js/model/shipping-save-processor-mixin.js` (new)
  — on save success clears `Magento_Ui/js/model/messageList` (same `.clear()` API OscPro
  cancel-coupon uses); guards against OscPro's promise-less early-return path.
- `app/code/Launchpad/Osc/view/frontend/requirejs-config.js` — +2 mixin registrations.
