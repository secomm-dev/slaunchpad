# Decision Record: Idempotency + lock for duplicate callbacks

## Context

Current dedup is status-based (`order status == pending`) only — two concurrent IPNs can both pass before either saves → **double invoice**; no transaction-id idempotency; no DB lock. Data-integrity + irreversible category.

## Decision (open — SA)

Use `vnp_TransactionNo` as the **idempotency key** + a **DB-level order/transaction lock** (`SELECT FOR UPDATE`) or a message-queue single-consumer. Duplicate/re-played callback → `RspCode '02'` with **no re-invoice / no re-state**.

## Alternatives

- Status-check only (race → double invoice — rejected).
- Application-level mutex (unreliable across nodes — rejected for multi-instance).

## Consequences

Guarantees exactly-once processing; DB lock adds contention (acceptable for IPN volume); queue option adds infra.

## Affected components

`Ipn.php` (process branch); payment/transaction write path.
