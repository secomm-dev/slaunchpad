# Decision Record: Spec-First governance (NO SPEC → NO IMPLEMENTATION)

<!-- CANONICAL DECISION STORE. PROPOSED 2026-08-17 — chờ SA/TL approve (Level 2: workflow governance). -->
<!-- Index pointer: `.ai/project-context/memory/DECISIONS.md` -->

## Context

Audit 2026-08-17 toàn bộ toolkit workflow phát hiện: tuy Mini-Spec concept tồn tại (template + Mode B guide) và một số chỗ đã yêu cầu spec (split-feature, state-model entry), invariant "mọi code change bắt đầu từ specification" KHÔNG được enforce nhất quán — có nhiều lối thoát: Planning-First Sequence bước 3 cho phép "ticket với AC" thay spec (Mode C); Gate 1/DoR áp "Full spec: C ❌ Not required"; ticket template có field Spec optional; implement-task/fix-bug/refactor-code/developer-agent chỉ check plan; validator KHÔNG có check spec nào; Mode D chỉ cần retro ticket 24h.

Requirement (SA/TL 2026-08-17): enforce bắt buộc — **Every code change starts from an explicit behavioral specification. Small task → embedded Mini-Spec; larger/higher-risk feature → Full Spec. No valid specification = no implementation.** Không weaken cho speed/quick fix/bug fix/direct command/agent delegation.

Level 2 (workflow governance — áp cho mọi coding task).

## Decision (proposed)

1. **Two-level specification.**
   - **MINI (embedded trong ticket)** — minimum sections: `Goal`, `Expected Behavior`, `Rules / Constraints`, `Out of Scope`, `Acceptance Criteria`. Thiếu `Expected Behavior` hoặc `Acceptance Criteria` ⇒ task KHÔNG executable. Áp: small bug fix, isolated/config/UI change, low-risk refactor, small integration, scope nhỏ + behavior rõ.
   - **FULL (file spec riêng, canonical cho feature)** — bắt buộc khi: reusable feature / multi-ticket / cross-module / architecture change / integration có lifecycle phức tạp / state machine / payment-shipping-fulfillment / BC quan trọng / shared-core capability / nhiều developer / high-risk / nhiều business rules. Full Spec đứng TRƯỚC ticket decomposition; mọi ticket con reference cùng canonical spec (không duplicate rules).
2. **NO SPEC → NO PLAN → NO CODE.** Xóa escape "or ticket with AC" khỏi Planning-First Sequence (bước 3: bắt buộc *valid specification* — Full reference hoặc embedded Mini-Spec). Mode C: "ticket + AC only" → "ticket + embedded Mini-Spec". Mode D: hotfix được inspect/log trước, nhưng code change phải có ít nhất inline short-spec (expected vs actual + AC), retro Mini-Spec ≤ 24h giữ nguyên và được nâng cấp yêu cầu.
3. **Classification trước artifacts:** incoming requirement → classify complexity/risk → specification level (MINI/FULL) → spec → validate → plan → implement → verify against spec. Plan PHẢI chứa dòng `Specification:` (path hoặc "Mini-Spec (embedded) — {ticket}"); plan không redefine behavior trái spec — conflict ⇒ quay lại spec stage.
4. **SpecificationGuard — defense in depth tại 4 layer:**
   - (a) **Rule:** `shared-core/rules/spec-first.md` (canonical invariant + classification triggers + executable-task definition); planning-first.md reference;
   - (b) **Gates/state:** Gate 1 (Requirement Gate) + Gate 3 + DoR + WORKFLOW_STATE_MODEL (entry Task Created/Planning/Implementing yêu cầu `spec_status = VALID`);
   - (c) **Entry-point functions/skills/agents:** implement-task, analyze-ticket, fix-bug, refactor-code, developer agent, task/spec skills, pre-task checklist — đều check spec trước;
   - (d) **Machine validator:** `bin/project-ai-validate --check-specs` — scan tickets/canonical records ở trạng thái executable (Ready / In Progress) + plans: yêu cầu spec reference hoặc embedded Mini-Spec đủ sections; **soft WARN mặc định, hard-fail dưới `SPEC_GATE_HARD=1`** (theo precedent `DEC_WORK_ITEMS_HARD`); contract-test fixtures S1–S6.
5. **Legacy tickets (backward compat):** KHÔNG migrate backlog; enforce khi ticket được **activate** (validator chỉ check trạng thái executable, không check Done/Dev-complete). Ticket cũ được chọn để execute ⇒ check spec ⇒ thiếu ⇒ sinh/đề xuất Mini-Spec hoặc Full Spec ⇒ validate ⇒ tiếp tục.
6. **AI không tự suy diễn missing requirements trong implementation** — spec thiếu behavior quan trọng ⇒ quay lại spec stage. Ngoại lệ: nội dung resolve trực tiếp từ code/architecture/project rules/canonical requirements ⇒ AI được bổ sung spec kèm nguồn evidence.
7. **Không over-document:** small task = Mini-Spec embedded (KHÔNG file riêng); feature = MỘT shared Full Spec. Mini-spec-template.md được bổ sung sections `Expected Behavior` + `Rules / Constraints`; ticket template: Spec field REQUIRED (path hoặc "Mini-Spec embedded").
8. **Verification quay lại spec:** DoD/Done yêu cầu ghi rõ spec nào được implement + AC nào pass + invariants nào verify (post-task checklist + testcase skill).

## Alternatives considered

- **Giữ "ticket + AC" cho Mode C** — rejected: AC là điều kiện hoàn thành, không phải behavioral contract (không có Expected Behavior/Rules/OoS) — đúng lỗ hổng đã được yêu cầu bịt.
- **Mini-Spec bắt buộc file riêng** — rejected: over-document cho bug 30 phút; embedded trong ticket đủ (§14).
- **Hard-fail validator mặc định ngay** — rejected cho giai đoạn đầu: legacy tickets đang active sẽ vỡ hàng loạt; soft-WARN mặc định + hard opt-in theo precedent DEC_WORK_ITEMS (flip sau khi backlog được bổ sung spec).
- **Chỉ sửa prompt/rules, không có validator** — rejected: prompt-only rule đã bị bypass hôm nay (audit chứng minh); machine check là layer bắt buộc.

## Consequences

- (+) Invariant được bảo vệ 4 layer; bypass paths bịt (Mode C/D, direct implement, fix-bug/refactor, agent delegation, generated ticket).
- (+) Nhẹ cho task nhỏ (embedded, không file mới) — workflow vẫn lightweight.
- (+) Feature spec canonical trước decomposition → chống architecture drift.
- (−) Mọi ticket mới phải có Mini-Spec tối thiểu — thêm ~vài phút each; legacy ticket khi activate phải bổ sung spec trước khi chạy.
- (−) Đồng bộ toolkit + project (rules/functions/templates/validator/AGENTS); validator soft mặc định → hard-flip là follow-up sau backfill.
- Mode D vẫn cho phép fix nhanh (inline short-spec expected-vs-actual + AC ngay trong commit/hotfix note) — không làm chậm incident response.
