# [SLP][BUG-M5NZFO] Enforce GHN Weight And Dimension Limits At Checkout

<!-- External ticket: SLP-209 [GHN][Checkout] GHN Express không chặn đơn hàng vượt giới hạn Maximum Weight ở trang Checkout. -->
<!-- Generated by Claude Code per bug-record-template (Mode C). -->
<!-- Related record: BUG-W3XTW4 (SLP-210) — same limit mismatch surfaces later as GHN sync failure. -->

## Summary

Carts over the configured GHN limits (package weight, dimensions, volumetric mass — Express "Maximum Weight" being the reported case) still see and select GHN Express/Standard at checkout. The per-carrier guards `GHN\Express::canDisplay()` and `GHN\Standard::canDisplay()` exist but were never invoked: the SLP-12 refactor added them without a call site in `GHN::collectRates()`, so no limit was ever applied when quoting rates. Orders that GHN cannot physically accept get quoted, placed, and only fail later at GHN portal sync (see BUG-W3XTW4 / SLP-210).

## Mini Spec

### Goal

Restore the intended rate-time filtering: a cart exceeding any GHN limit for a service must not see that service at checkout.

### Expected Behavior

- `GHN::collectRates()` returns `false` (no rates) when `canDisplay()` fails for the current carrier, so the method disappears from checkout.
- Package-level checks (length/width/height, weight in kg, volumetric `(L×W×H)/5000`) and Standard's item-level checks run with the admin advanced-settings values, falling back to each carrier's own `MAX_*` consts.
- No runtime error when package dims are unset (null) on some collect-rates paths.

### Constraints / Rules

- Shipping module (Secomm_GiaoHangNhanh) — TL review required per `CLAUDE.md` (done: user approved wiring on 2026-09-14).
- Admin advanced-settings config paths (`carriers/ghn/advanced_settings/{code}/…`) keep precedence over code defaults.
- Guard must not change pricing — only whether the method is offered.
- Standard stays stricter than Express (item-level validation remains Standard-only, by design).

### Out of Scope

- The 150cm create-order API limit vs 200cm checkout-guard defaults mismatch (order 95 class of bugs): lowering `MAX_LENGTH`/`maximum_length` to 150 is a separate pending decision (config change vs const change).
- Split-shipment support for carts that cannot ship as one GHN parcel.
- Catalog data cleanup for products missing/abusing dimension attributes.
- Unit test infrastructure for GHN carriers (deferred until CI work).

### Acceptance Criteria

- AC-001: Cart with package weight over the Express limit (default 50 kg) → GHN Express not offered at checkout; Standard unaffected if within its limits.
- AC-002: Cart over any Standard package/item limit (default 20 kg package) → GHN Standard not offered.
- AC-003: Normal carts still receive GHN rates and can place orders.
- AC-004: Rate collection with unset package dimensions does not throw (`ceil(null)` TypeError).

## Steps to Reproduce

1. Enable GHN Express; keep advanced settings at defaults (Maximum Weight 50 kg).
2. Add products to cart so package weight exceeds 50 kg; proceed to checkout with a GHN-eligible address.
3. Observe GHN Express still listed and quotable at checkout.
4. Place the order — it later fails GHN portal sync with a limit error (e.g. `LENGTH_IS_OVER_LIMIT`).

## Expected Behavior

GHN Express is hidden from checkout when the package exceeds its weight (or dimension/volumetric) limit; only shippable carts can select and place GHN orders.

## Actual Behavior

GHN Express (and Standard) were always quoted regardless of limits — `canDisplay()` had no caller since install (commit ad019055, SLP-12), so checkout never applied any GHN constraint.

## Root Cause

1. **Missing call site (primary):** SLP-12 refactor introduced `abstract GHN::canDisplay()` plus both implementations, but `collectRates()` only calls `estimateShippingCost()` — the guards were dead code. Module README §2.1 documents them as active (docs drifted).
2. **Wrong effective limits (config layers):** the `?:` const fallbacks never fire because module `etc/config.xml` sets non-empty `advanced_settings` defaults — and Standard's were 10x typos (20000cm dims, 5000000g = 5000kg package, 50kg item weight over a 20kg package, 200kg item volumetric under a 1600kg package). On top of that, `core_config_data` rows (deployed-config import) pin those same wrong values, so fixing `config.xml` alone does not change runtime on any env where the rows exist.
3. **Latent defects in the dormant guards** (uncovered while wiring):
   - `Standard::getDefaultValueItem()` fallbacks were a copy of Express package consts (50 kg / 200 kg) contradicting Standard's own (20 kg / 1600 kg).
   - Package weight compared with strict `<` in Standard vs `<=` in Express; item dims compared as raw strings against ints.
   - `ceil($request->getPackageLength())` throws TypeError on PHP 8 when package dims are null (same hazard already noted in `ShippingDetailsDataBuilder`).
4. **200 vs 150 gap:** checkout guard defaults allowed 200cm while the GHN create-order API rejects length > 150 (the order-95 / SLP-210 failure class) — fee API tolerates 200, so such carts quoted fine and failed at sync.

## Fix

- `GHN::collectRates()`: early `return false` when `!$this->canDisplay($request)` — guard now runs before the fee API call.
- `Standard`/`Express::canDisplay()`: collapsed nested conditionals into a single boolean return; removed stale "no limit" comment; weight comparison unified to `<=`; `(float)` cast before `ceil()` for null-safe dims.
- `Standard::validateDataProduct()`: fallbacks switched from `getDefaultValueItem()` array to the carrier's own `self::MAX_*` consts; `validItemOrder()` compares int-cast locals; `getDefaultValueItem()` deleted.
- `etc/config.xml`: Standard defaults corrected to its consts (200cm / 20000g / 20000g item / 1600000g item volumetric); `maximum_length` set to **150** for both services (proven create-order API limit — width/height kept at 200 until GHN proves otherwise); `MAX_LENGTH` consts aligned to 150.
- **Local env data fix:** corrected the pinned `core_config_data` rows (default scope) in the staging-snapshot DB to the same values. **Rollout note: staging/prod need the equivalent config data fix (admin re-save or SQL) — code-only deploy will NOT change limits on envs where the rows exist.**

Net: −28 lines across 3 carriers + config.xml; `php -l` clean.
