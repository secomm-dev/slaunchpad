# [SLP][BUG-W3XTW4] Surface real GHN sync error and stop multiplying item dimensions by qty

<!-- External ticket: SLP-210 [GHN][Order admin] Order cannot sync to GHN portal. -->
<!-- Generated by Claude Code per bug-record-template (Mode C). -->

## Summary

Admin order sync to GHN fails (HTTP 400, e.g. `LENGTH_IS_OVER_LIMIT`) but every caller — admin Sync controller, `sales_order_place_after` observer, queue consumer — only surfaces the hardcoded string `Something went wrong when synchronize order.`. The real GHN error (`message` / `code_message` / `code_message_value`) is discarded inside `SynchronizeOrderValidator`, so support cannot tell why an order fails to sync. A second defect in the same request path: `SynchronizeOrderDataBuilder::getItems()` multiplies item length/width/height by ordered qty, sending dimensionally wrong values (e.g. 3 units of a 100cm item become a 300cm line).

## Mini Spec

### Goal

Sync failures show the actual GHN error message to admin/logs, and per-item dimensions sent to GHN are per-unit (qty is already a separate field GHN receives).

### Expected Behavior

- On GHN error response, exception message contains the real GHN `message` (fallback `code_message_value`), e.g. `GHN sync failed: Kích thước (dài) vượt quá mức cho phép: 150`.
- Item `weight`/`length`/`width`/`height` in the `shipping-order/create` payload equal the per-unit product attributes (ceil-ed, per GHN docs example); order-level `weight` stays the order total in grams.

### Constraints / Rules

- Shipping module (Secomm_GiaoHangNhanh) — TL review required per `CLAUDE.md` (done: user approved fix on 2026-09-14).
- Validator contract unchanged: still fails when `message !== 'Success'`; only the error text changes.
- `CancelOrderValidator` shares the same parent — fix both via one helper on `AbstractResponseValidator`.

### Out of Scope

- Catalog data cleanup (product `throw-chunky-knit` has `length = 300` and weight rendering as 600kg in GHN payload — bad product attributes, not code).
- Dims aggregation strategy change (e.g. max-across-items instead of per-unit) — add if GHN starts rejecting per-unit dims.
- Retry/requeue behavior of `ghn.sync.order` consumer.

## Steps to Reproduce

1. Place an order with GHN shipping where item dims exceed GHN limits (e.g. product length > 150cm, service 100039 "Hàng nặng").
2. Admin → Order → Sync (direct mode), or place order with auto-sync enabled.
3. Observe error shown/logged: `GHN sync failed: Something went wrong when synchronize order.` — no hint of the real cause.

## Expected Behavior

Error surfaces the real GHN response message, e.g. `GHN sync failed: Kích thước (dài) vượt quá mức cho phép: 150` (`code_message: LENGTH_IS_OVER_LIMIT`).

## Actual Behavior

Hardcoded generic message; real GHN fields (`message`, `code_message`, `code_message_value`) discarded at [SynchronizeOrderValidator.php](../../../app/code/Secomm/GiaoHangNhanh/Model/Service/Validator/SynchronizeOrderValidator.php) before `ServiceCommand` throws `CommandException`.

## Root Cause

1. `SynchronizeOrderValidator::validate()` (and `CancelOrderValidator`) replace the failed response with a fixed `__('Something went wrong...')` phrase; `AbstractResponseValidator::validateResponseMsg()` only returns a bool and never extracts the error text. `ServiceCommand` then throws `CommandException` with that generic text as the only message.
2. `SynchronizeOrderDataBuilder::getItems()` multiplied per-unit product dims by `qtyOrdered` — dimensionally wrong (dims don't scale linearly with units) and pushes lines over GHN's 150cm limit for multi-qty orders.

## Fix

- `AbstractResponseValidator`: new `getGhnErrorMessage(array $response): string` — returns `message`, fallback `code_message_value`, else empty.
- `SynchronizeOrderValidator`: error phrase → `GHN sync failed: %1` with the real message.
- `CancelOrderValidator`: error phrase → `GHN cancel failed: %1` (same disease).
- `SynchronizeOrderDataBuilder::getItems()`: removed `× quantity` from `weight`/`width`/`height`/`length` — per [GHN create-order docs](https://developer.ghn.vn/en/docs/order/create), `items[]` values are per-unit (docs example: item 300g × qty 2 = root weight 600g total; GHN multiplies by `quantity` itself).
- `SynchronizeOrderDataBuilder::build()`: root `length`/`width`/`height` computed as per-axis sum of item dims × qty (same convention as `Secomm\Base\Plugin\Model\Shipping::getTotal()` used for rate requests) instead of hardcoded `1,1,1`.
- `ShippingDetailsDataBuilder::getAllItems()` (checkout fee request): same per-unit fix as `getItems()` so quoted fee uses the same payload semantics as order creation.
- Follow-up (caught in test, TypeError `ceil(string)`): product/quote-item dim attributes load as strings — old code's `× qty` masked the coercion. Both builders now cast `(int)ceil((float)…)` on the three dims.

Docs cross-check 2026-09-14: unit conversions correct (config `general/locale/weight_unit` kgs→×1000g, lbs→×453.59g; root weight = order total → grams). Root dims docs: required for `service_type_id=2`, max 200cm each — sums can now exceed 200 and GHN will reject with a real message (surfaced by the validator fix).
